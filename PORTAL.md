# Stable Structure staff portal

Timesheets, approvals, reports and GST invoicing for the Stable Structure team.
Replaces the shared workbook `Timesheet- Version 02.xlsm`.

It is part of the Stable Structure website and deploys in the **same Vercel
project**: staff reach it at **www.stablestructure.co.nz/portal** (the "Staff
login" link in the header and footer, or the shortcuts `/login`, `/staff`,
`/timesheet`).

How the two halves share one app:

- The repo is a Next.js app. Every portal route lives in `app/portal/`.
- The marketing site is still generated by `build/generate.js` into the repo
  root, exactly as before. `build/copy-public.mjs` then copies the publishable
  files (HTML, `styles.css`, `main.js`, `assets/`, `services/`, `guides/`,
  `robots.txt`, `sitemap.xml`) into `public/`, which Next serves at the site root.
  Nothing else in the repo (generator, reports, SQL, config) is ever published.
- `next.config.ts` carries the redirects and headers that used to be in
  `vercel.json`, plus `/` -> `index.html`. `app/[...missing]/route.ts` serves the
  site's own `404.html` with a real 404 status.
- `proxy.ts` only runs for `/portal/*`; marketing pages are plain CDN files.

## Stack

- Next.js 16 (App Router, `proxy.ts` for the session check and flood protection), TypeScript, Tailwind 4
- Supabase: Postgres, Auth (invite-only, email + password), row-level security
- Project ref `opfdfyxkwevkyyyaiifv`

## Run locally

```bash
npm install
cp .env.example .env.local   # fill in the two NEXT_PUBLIC_SUPABASE_* values
npm run dev -- --port 4410   # website at http://localhost:4410, portal at /portal
```

`npm run build && npm run start` reproduces production, redirects and headers included.

## Database

`supabase/migrations/` holds the schema in order; `supabase/all-migrations.sql`
is the same four files concatenated for pasting into the Supabase SQL editor.

| Migration | Contents |
|---|---|
| `0100_schema` | tables: settings, profiles, clients, projects, project_rates, work_types, time_entries, entry_billing, invoices, audit_log |
| `0200_security` | roles, RLS policies, audit triggers, auto-profile on new auth user |
| `0300_workflow_and_reports` | `approve_entries`, `return_entries`, `create_invoice`, `void_invoice`, `hours_check`, `project_summary`, views |
| `0400_seed_lists` | work types, clients and projects from the workbook's Lists sheet |
| `0500_public_holidays` | NZ + Auckland public holidays 2025-2028; holiday-aware `hours_check` |
| `0600_rate_limits` | shared rate-limit counters, callable only by the server |
| `0700_external_invoices` | `invoices.is_external` + `record_external_invoice` for time billed from another system |
| `0800_leave` | annual / sick / bereavement / parental leave requests (half days), `v_leave_calendar` (type hidden from other staff), `leave_balances` with carry-over via `app.leave_balance` (opening balances + anniversary accrual, sick capped), `decide_leave`, leave-aware `hours_check` |
| `0900_leave_balance_booked` | balance deducts approved leave booked for the future too |

Roles: `employee` (own time only, never sees rates or values), `approver`
(all time, rates, approve / return), `admin` (approver + setup + invoices).
All of it is enforced in the database; the app only decides what to show.

## Rate limiting

Two layers, both in code:

1. **Flood protection** (`proxy.ts`, per IP, per server instance, in memory):
   300 requests/min to `/portal`, 60 writes/min, 20 writes/min on the
   signed-out pages. Over the limit -> `429` with `Retry-After`. The marketing
   pages never reach this code; they are static files on the CDN.
2. **Abuse limits** (`lib/rate-limit.ts`, counted in the database so they hold
   across instances): sign-in 5 per email and 20 per IP per 15 min; password
   reset 3 per email and 10 per IP per hour; password changes 10/hour; staff
   invites and sign-in links 30/hour; Excel/PDF downloads 30 per 5 min; My day
   saves 120 per 5 min; approve / return / invoice actions 60 per 5 min; invoice
   emails 20/hour. Needs `SUPABASE_SERVICE_ROLE_KEY` and migration `0600`;
   without them it falls back to the in-memory counter rather than failing.

Requests are also size-capped: 50 entries per day, 500 ids per bulk action,
500-character descriptions. Supabase Auth applies its own limits on top.

## Keeping the free database awake

Free Supabase projects pause after about a week without activity. Vercel Cron
(`crons` in `vercel.json`) calls `/portal/auth/keepalive` every day at 18:00 UTC
(6 am NZST); it runs one real query using the service key. Check it under
Vercel -> project -> Cron Jobs, or open the URL yourself: `{"ok":true,...}`.
Optional: set `CRON_SECRET` in Vercel to restrict the endpoint to Vercel's cron.
This is a workaround, not a backup. Delete the `crons` entry after moving to
Supabase Pro.

## Deploying (existing Vercel project)

No new project and no settings to change: `vercel.json` on this branch tells
Vercel the framework is Next.js and the build command is `npm run build`.

1. Add the environment variables above to the existing project (Production and
   Preview), with `NEXT_PUBLIC_APP_URL=https://www.stablestructure.co.nz`.
2. Push this branch. Vercel builds a **preview deployment**; check the website
   and `/portal` there before merging. `main` is untouched until you merge.
3. Supabase -> Authentication -> URL Configuration: Site URL
   `https://www.stablestructure.co.nz/portal`; Redirect URLs
   `https://www.stablestructure.co.nz/portal/**`, `http://localhost:4410/portal/**`
   and the preview domain if you want to test sign-in links there.
   Keep public sign-ups off.
4. Merge to `main` (and mirror to `prod` as usual).
